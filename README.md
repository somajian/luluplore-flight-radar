# 機票價格雷達 — GitHub Pages 部署說明

## 檔案清單（全部都要上傳到 repo）

- `index.html` — 網頁主結構
- `style.css` — 所有樣式（含亮／暗色模式）
- `data.js` — 機票歷史資料（純前端 JS 變數，無需後端）
- `script.js` — 網站互動邏輯（含匿名查詢紀錄的呼叫）
- `supabase-config.js` — 你的 Supabase 連線設定（要自己填 URL / key，見下方）

五個檔案放在同一層資料夾即可，路徑都是相對路徑，不需要調整。

## 部署到 GitHub Pages 的步驟

1. 建立一個新的 GitHub repository（public 或 private 皆可，但 Pages 免費方案通常要 public repo，或使用有 Pages 權限的 private repo）。
2. 把這五個檔案上傳到 repo 的根目錄（或 `/docs` 資料夾，看你要選哪個當發佈來源）。
3. 到 repo 的 **Settings → Pages**。
4. Source 選擇 `Deploy from a branch`，Branch 選 `main`（或你上傳檔案的分支），資料夾選 `/ (root)`（或 `/docs`，視你放檔案的位置而定）。
5. 儲存後，GitHub 會給你一個網址，格式通常是：
   `https://<你的帳號>.github.io/<repo名稱>/`
6. 等 1 ～ 2 分鐘讓 GitHub 部署完成，就可以直接用瀏覽器打開這個網址。

## 🔌 Supabase 設定（記錄匿名查詢紀錄用）

這個版本已經接好「使用者按下『查一下』、結果正常顯示之後，再把這次查詢匿名寫入 Supabase」的程式碼，資料表叫 `flight_radar_events`，記錄的欄位跟網站頁尾的隱私權政策完全對得上：event_type、出發地、目的地、航空公司類型、輸入的機票價格、查詢結果的百分位、查詢時間。

機票歷史資料本身（`data.js` 裡的 419 筆）**沒有**搬去 Supabase，還是照舊放在前端檔案裡。

### 步驟 1：建立 Supabase 專案

1. 到 [supabase.com](https://supabase.com) 註冊／登入，點「New project」。
2. 幫專案取名（例如 `luluplore-flight-radar`），選一個離台灣近的 region（例如 Singapore），設定資料庫密碼（這組密碼是給你自己用的，不會放進網站程式碼）。
3. 等專案建立完成（約 1～2 分鐘）。

### 步驟 2：建立資料表

在 Supabase 後台左側選 **SQL Editor**，貼上以下指令並執行：

```sql
create table flight_radar_events (
  id bigint generated by default as identity primary key,
  event_type text not null default 'price_check' check (event_type = 'price_check'),
  origin text,
  destination text not null,
  airline_type text,
  price integer,
  percentile integer check (percentile between 0 and 100),
  created_at timestamptz not null default now()
);

-- 開啟 RLS（Row Level Security）—— 這是整個匿名紀錄功能安全性的核心，
-- 沒有這一步，任何人只要打開瀏覽器 devtools 看到你的 key，就能讀光整張表。
alter table flight_radar_events enable row level security;

-- 只開放「新增」(insert) 給匿名使用者，且只能是 price_check 事件；
-- 不開放「讀取」(select)、修改 (update)、刪除 (delete) 給任何前端角色。
-- 這樣即使有人在瀏覽器 devtools 裡看到你的 publishable/anon key，
-- 也只能新增一筆查詢紀錄，沒辦法看到別人查過什麼、也沒辦法竄改或刪除既有資料。
create policy "anon can insert price_check events"
on flight_radar_events
for insert
to anon
with check (event_type = 'price_check');

-- 沒有幫 anon／authenticated 角色建立任何 select / update / delete policy，
-- 在 RLS 底下「沒有 policy = 完全不能做那個操作」，所以前端天生就讀不到
-- 這張表的任何一筆資料 —— 這就是題目要求的「避免前端可以直接讀取整張表」。
```

執行成功後，左側 **Table Editor** 應該就能看到 `flight_radar_events` 這張表。

### 步驟 3：取得 Project URL 和前端要用的 key

1. 後台左側選 **Settings → API Keys**（或首頁的「Connect」按鈕）。
2. 複製 **Project URL**（長得像 `https://xxxxxxxxxxxx.supabase.co`）。
3. 複製 **Publishable key**（新版介面顯示的名稱，通常是 `sb_publishable_...` 開頭；如果你的專案介面還是舊版、顯示的是 **anon public** 這組 key（一長串 JWT），用那組也可以，效果一樣）。

   ⚠️ **絕對不要複製 Secret key（或舊版叫 `service_role` key）**！那組 key 可以繞過 RLS、讀寫整個資料庫，只能用在後端伺服器，這個網站完全用不到它，也絕對不能出現在任何前端檔案裡。

### 步驟 4：填入 `supabase-config.js`

打開 `supabase-config.js`，把這兩行換成你剛剛複製的值：

```js
var SUPABASE_URL = 'https://xxxxxxxxxxxx.supabase.co';
var SUPABASE_ANON_KEY = '你的 Publishable key（或 anon public key）';
```

存檔、上傳到 GitHub（覆蓋原本的檔案）就完成了。之後每次有人在網站上按「查一下」、看到結果之後，就會自動、匿名地在 `flight_radar_events` 表多一筆紀錄。

### 沒填 / 填錯的情況

如果 `supabase-config.js` 還是預設的 `YOUR-PROJECT-REF` / `YOUR-ANON-PUBLIC-KEY`，或是網路連不到 Supabase，查票功能完全不受影響 —— 只是不會寫入紀錄，瀏覽器主控台會印一行提醒（一般使用者看不到，也不會跳出任何錯誤畫面，不會擋住查詢結果顯示）。

## 📋 照妳附的指令，逐項回答

1. **要建立什麼 table**：`flight_radar_events`（步驟 2 的 SQL）。
2. **每個欄位的型態**：`id` bigint（自動遞增主鍵）／`event_type` text（固定值 `price_check`）／`origin` text（可為空，「不分出發地」時會是 null）／`destination` text（必填）／`airline_type` text（`all`／`legacy`／`lcc`）／`price` integer／`percentile` integer（限制 0～100）／`created_at` timestamptz（資料庫自動產生）。
3. **RLS 要怎麼設定**：`alter table flight_radar_events enable row level security;`（步驟 2 已包含）。
4. **要建立哪些 policies**：只建立一個 —— 允許 `anon` 角色 `insert`、且限定 `event_type = 'price_check'`；不建立任何 select/update/delete policy，等於前端完全不能讀取、修改、刪除。
5. **GitHub Pages 前端要用哪個 key**：**Publishable key**（新版介面的名稱），或舊版介面的 **anon public** key，兩者擇一填進 `supabase-config.js`。
6. **哪些 key 絕對不能放在前端**：**Secret key**（新版介面）／**`service_role` key**（舊版介面）—— 這兩個名字指的是同一種東西，任何情況都不能出現在 `index.html`、`script.js`、`supabase-config.js`，或任何會上傳到 GitHub 的檔案裡。
7. **JavaScript 哪個檔案負責 Supabase**：連線設定在 `supabase-config.js`；實際寫入的邏輯是 `script.js` 裡的 `logPriceCheckEvent()` 函式，`checkBtn` 的查詢結果全部渲染完成後才會呼叫它。
8. **需要修改哪些檔案**：這次是 `index.html`（引入 Supabase JS 函式庫 + `supabase-config.js`）、`script.js`（`logPriceCheckEvent` 邏輯、表名／欄位名）、`supabase-config.js`（連線設定）。查票雷達本身的計算邏輯、版面、視覺設計完全沒有更動。
9. **完成後怎麼測試**：填好 `supabase-config.js` 並上傳到 GitHub 後，打開網站，按 F12 開瀏覽器開發者工具的 Network 分頁，篩選 `flight_radar_events`，然後在網站上正常查一次票 —— 應該會看到一個對 Supabase 的 POST 請求，狀態碼 201 表示成功寫入；Console 分頁如果有 `[Luluplore]` 開頭的警告文字，代表寫入失敗但查票功能仍正常（可以點開看警告內容判斷原因，例如 key 填錯、RLS policy 沒建好等）。
10. **如何確認匿名 price_check 已成功寫入**：回到 Supabase 後台 → **Table Editor** → `flight_radar_events`，重新整理應該就能看到剛剛那筆新紀錄，`event_type` 是 `price_check`、`created_at` 是查詢當下的時間。

## ❓ 之後機票資料更新，是不是請你出新的 HTML 貼到 GitHub 就好？

分兩種情況：

- **只是更新機票歷史資料（最常見）**：把新的資料重新整理進 `data.js`（維持 `const FLIGHT_DATA = {...};` 這個格式），**只需要覆蓋上傳 `data.js` 這一個檔案**到 GitHub 就好，`index.html` / `style.css` / `script.js` / `supabase-config.js` 都不用動、也不用重新產生。GitHub Pages 會在你更新後自動重新部署（通常 1 分鐘內）。
- **如果之後功能有調整**（例如版面、比價邏輯、隱私權文字這類變動）：那我會像這次一樣，直接改對應的檔案（`index.html`／`style.css`／`script.js`），再請你覆蓋上傳有變動的那幾個檔案就好，不是每次都要整包重貼。

所以簡單說：**平常更新資料只需要換 `data.js`；改功能才需要換對應的檔案**，不用每次都整份重新上傳。

## 確認事項

- 沒有登入、沒有會員系統 — 全部使用者都可以直接用。
- 機票歷史資料在 `data.js` 裡，開啟頁面就是完整功能，就算 Supabase 沒設定也一樣能查票、比價。
- 唯一會主動送出資料的動作，是使用者按下「查一下」、看到結果之後，把（event_type／出發地／目的地／航空公司類型／輸入價格／百分位）這幾個欄位匿名寫進 Supabase 的 `flight_radar_events` 表；查詢時間由資料庫自動記錄，不會經過瀏覽器端組出時間戳記，也不會記錄姓名、Email、電話、LINE ID、會員 ID 或 IP 位址這類可識別身分的資訊。
- 不依賴 Claude Artifact 環境，純 HTML／CSS／JS，file:// 本機開啟或 GitHub Pages 的 https:// 都可以正常運作（Supabase 寫入需要網路連線，本機離線測試時會自動略過，不影響其他功能）。
- 其他外部連線：Google Fonts（載入字體）、Supabase JS 函式庫（透過 jsDelivr CDN 載入）。若被擋掉，頁面會 fallback 成系統字體／略過查詢紀錄，不影響查票與比價功能。
